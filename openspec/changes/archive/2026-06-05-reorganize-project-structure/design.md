## Context

Проект состоит из ~8 компонентов, 2 страниц, 1 хука, и имеет плоскую структуру `src/` с группировкой по техническому признаку (`components/`, `hooks/`, `pages/`). Текущая структура не отражает доменную связанность кода и будет мешать навигации по мере роста. Выполняется рефакторинг без изменения бизнес-логики — только перемещение файлов и обновление import-путей.

## Goals / Non-Goals

**Goals:**
- Внедрить FSD-light с шестью слоями (app → pages → widgets → features → entities → shared)
- Сгруппировать код по доменам: типы и утилиты рядом с entity, хуки рядом с данными
- Выделить user actions в отдельные feature-модули
- Создать barrel-файлы (index.ts) для публичного API каждого модуля
- Обновить все import-пути

**Non-Goals:**
- Изменение логики компонентов, хуков или стилей (чистый рефакторинг)
- Декомпозиция `useSubscriptions` — хук остаётся монолитным
- Добавление новых возможностей или UI-компонентов

## Decisions

### Decision 1: FSD-light вместо полного FSD

**Решение:** Используем шесть слоёв FSD (app, pages, widgets, features, entities, shared) без обязательных слайсов внутри сущностей (Subscription — единственная сущность, выделять `subscriptions/` слайс внутри entities избыточно).

**Почему не полный FSD:**
- В проекте одна сущность и ~8 компонентов — следовать FSD-букве со слайсами, сегментами и строгими правилами линтинга — overkill
- FSD-light сохраняет главное (слои и направление зависимостей), но без лишнего boilerplate

### Decision 2: entities/subscription/lib/useSubscriptions.ts

**Решение:** Хук `useSubscriptions` размещается в `entities/subscription/lib/useSubscriptions.ts`, а не в `shared/lib/`.

**Почему:**
- В shared кладут переиспользуемый код без бизнес-логики — `useSubscriptions` содержит схему данных, валидацию и версионирование
- Рядом с `calcProgress` — вся бизнес-логика сущности Subscription в одном модуле
- В текущем проекте Visit — вложенный массив в Subscription, выделять отдельную entity нет смысла

### Decision 3: widgets/subscription-detail и widgets/visit-timeline — отдельные виджеты

**Решение:** Разделяем, несмотря на единственного потребителя (SubscriptionPage).

**Почему:**
- Разные причины для изменений: макет страницы vs UX таймлайна (свайп, редактирование даты)
- VisitTimeline самодостаточен: своё состояние, свои эффекты, своя логика свайпа
- В FSD виджеты могут импортировать друг друга — это разрешено

### Decision 4: Кнопка "Отметить занятие" — отдельный feature

**Решение:** Извлечь кнопку mark-visit из SubscriptionDetail в `features/mark-visit/ui/MarkVisitButton.tsx`.

**Почему:**
- Каждое пользовательское действие = отдельный feature согласно FSD
- SubscriptionDetail перестаёт дирижировать действиями — он только отрисовывает слоты
- Согласованность: `features/` становится картой возможностей приложения
- Готовность к росту — будущие features (edit-subscription-name, delete-subscription) будут следовать тому же паттерну

## Risks / Trade-offs

- **Risk: Рефакторинг сломает import-пути** → Покрыто тестами; после рефакторинга запустить `npm test` и `npm run build`
- **Risk: VisitTimeline останется недозагруженным при SubscriptionDetail** → В FSD это нормально — виджеты могут импортировать виджеты
- **Trade-off: Один лишний файл MarkVisitButton.tsx для кнопки в 7 строк JSX** → Плата за консистентность архитектуры и читаемость карты возможностей
