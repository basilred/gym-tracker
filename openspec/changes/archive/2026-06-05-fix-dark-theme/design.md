## Context

Приложение использует CSS custom properties (design tokens) в `src/styles/tokens.css` для стилизации. Токены определены в `:root` (светлая тема) и переопределены в `@media (prefers-color-scheme: dark)` (тёмная тема).

**Текущая проблема:** токен `--color-surface` используется в двух несовместимых ролях:
1. Как цвет фона карточек и поверхностей — в тёмной теме `#16213e` ✓
2. Как цвет текста на кнопках (MarkBtn, SubmitBtn, DeleteBtn) — в тёмной теме `#16213e` ✗ (контраст 2.6:1)

Кнопки используют `color: var(--color-surface)` в предположении, что `--color-surface` всегда светлый. Это нарушено в тёмной теме.

Дополнительно:
- Input/Select не имеют `background-color`, наследуют `--color-bg` от body, который сливается с `--color-surface` формы
- ErrorBoundary не имеет CSS-классов, fallback UI полностью не стилизован

## Goals / Non-Goals

**Goals:**
- Контраст текста на кнопках ≥ 4.5:1 в обеих темах (WCAG AA)
- Поля ввода визуально различимы на фоне формы в тёмной теме
- ErrorBoundary fallback имеет стилизованный вид в обеих темах
- Решение минимально — правки только в токенах и компонентах, без изменения компонентной структуры

**Non-Goals:**
- Полный редизайн компонентов
- Добавление переключателя темы (пока только `prefers-color-scheme`)
- Глобальная переработка дизайн-системы
- Тестирование на реальных устройствах (только визуальная проверка через devtools)

## Decisions

### Decision 1: Добавить семантические токены вместо хардкода `#fff`

**Выбрано:** новые токены `--color-on-primary`, `--color-on-danger`, `--color-input-bg`.

**Альтернатива:** хардкодить `color: #ffffff` в каждом компоненте.
- Отклонено: нарушает принцип дизайн-системы. При изменении дизайна пришлось бы менять каждый файл.

```css
/* tokens.css */
:root {
  --color-on-primary: #ffffff;  /* текст на синих кнопках */
  --color-on-danger: #ffffff;   /* текст на красных кнопках */
  --color-input-bg: #ffffff;    /* фон полей ввода */
}

@media (prefers-color-scheme: dark) {
  :root {
    --color-on-primary: #ffffff;   /* остаётся белым */
    --color-on-danger: #ffffff;    /* остаётся белым */
    --color-input-bg: #0f172a;    /* чуть темнее поверхности */
  }
}
```

### Decision 2: `--color-input-bg` темнее `--color-surface`

В светлой теме input bg = `#ffffff` = то же, что surface. Но поля выделены рамкой (`--color-border`).

В тёмной теме input bg = `#0f172a` (slate-900) — немного темнее `--color-surface: #16213e`. Это создаёт эффект «вдавленности», типичный для dark UI.

**Альтернатива:** input bg = surface + просто рамка.
- Отклонено: в тёмной теме границы `#374151` (серый) и фон `#16213e` (тёмно-синий) недостаточно контрастны, поля теряются.

### Decision 3: ErrorBoundary — добавить CSS-классы, не трогая логику

Существующий ErrorBoundary — классовый компонент без стилей. Достаточно добавить className в render и создать минимальный CSS-файл.

**Альтернатива:** переписать на функциональный компонент.
- Отклонено: выходит за рамки задачи. Меняем только стилизацию.

### Decision 4: Не добавлять `--color-on-disabled`

Disabled-кнопка наследует `--color-on-primary`, но на сером фоне `--color-disabled`. В тёмной теме `#ffffff` на `#6b7280` имеет достаточный контраст (~4.5:1). Отдельный токен не нужен.

## Token Mapping After Changes

```
Token                   Light        Dark          Role
──────────────────────────────────────────────────────────
--color-on-primary      #ffffff      #ffffff       text on primary bg
--color-on-danger       #ffffff      #ffffff       text on danger bg
--color-input-bg        #ffffff      #0f172a       input/select bg
```

## Risks / Trade-offs

- **Риск:** `--color-input-bg: #0f172a` может не подойти при смене общей палитры → Минимизировано: токен в одном месте, легко поменять
- **Риск:** ErrorBoundary стили могут конфликтовать с глобальными сбросами → Минимизировано: используем БЭМ-классы `.ErrorBoundary-*`
- **Trade-off:** `--color-on-primary` и `--color-on-danger` сейчас оба `#ffffff`. Их разделение избыточно сейчас, но даёт гибкость в будущем (например, тёмный текст на жёлтых warning-кнопках)
